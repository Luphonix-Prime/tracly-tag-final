# Database Architecture and Operations Guide

This guide covers local database setup, operations (resetting, seeding, database studio), and production deployment guidelines for TraclyTag.

---

## 📂 Core Structure

TraclyTag uses **Drizzle ORM** with **libsql/SQLite** for its database layer. The configuration and schemas are centralized in the database workspace, while the backend API server maps client connections directly to the sqlite database file.

## 🛠️ Local Development Operations

Several convenience scripts are exposed from the workspace root to make managing the database straightforward.

### 1. Resetting & Seeding Demo Mock Data
Running the seed script completely truncates the existing tables (cleaning up historical scans, codes, and user accounts) and seeds a clean set of standard mock values including companies, operator logins, sample products, batches, codes, and pre-logged customer scans.

To execute the seed script, run this from the workspace root:
```bash
pnpm db:seed
```

> [!IMPORTANT]  
> The default mock operator logins generated by the seed script are:
> * **Master Admin**: `master` / `master123`
> * **Client Admin**: `demo_admin` / `admin123`
> * **Operator**: `demo_op` / `op123`

### 2. View Database (Drizzle Studio)
To spin up the web-based interactive console (Drizzle Studio) to browse data, edit records, or verify tables manually:
```bash
pnpm db:studio
```
The studio will launch locally at [http://localhost:4983](http://localhost:4983) by default.

### 3. Pushing Schema Changes
If you modify schemas inside [`lib/db/src/schema/`](file:///c:/Users/Keval/Documents/tracelytag/my-merger/tracly-tag-final/lib/db/src/schema/), push the updates directly to the database file:
```bash
# Push schema updates
pnpm --filter @workspace/db run push

# Force push (if schema changes conflict with existing SQLite data)
pnpm --filter @workspace/db run push-force
```

## 🚀 Production Deployment & Readiness

To make the database setup production-ready, transition from a local SQLite file to a cloud-hosted libsql database (such as **Turso**).

### 1. Environment Variable Configuration
The client code uses the `DATABASE_URL` environment variable. In production, configure your hosting provider (Vercel, AWS, etc.) with the cloud connection string and authentication token:

```env
# Connection String (e.g., Turso DB URL)
DATABASE_URL=libsql://your-database-name-user.turso.io

# Auth Token (For cloud authorization)
DATABASE_AUTH_TOKEN=your_turso_auth_token_here
```

### 2. Production Schema Migrations
For local development, `drizzle-kit push` is convenient because it alters the database directly. However, in production, you should use **safe migrations** to avoid data loss.

#### Step A: Generate migration files
Run Drizzle Kit's generator to produce SQL migration scripts based on schema diffs:
```bash
pnpm --filter @workspace/db exec drizzle-kit generate
```
This generates SQL files inside `lib/db/drizzle/`.

#### Step B: Execute migrations in Production
Integrate the migration runner script into your production deployment pipeline to apply pending updates before launching the main server process:
```bash
pnpm --filter @workspace/db exec drizzle-kit migrate
```

### 3. Connection Pooling and Security
* **Access Control**: Keep `DATABASE_AUTH_TOKEN` secret. Ensure production databases only accept secure HTTPS/WSS database connections.
* **Backups**: If continuing to use a self-hosted SQLite file in production, implement automated cron backups (e.g., `sqlite3 backup`) or use Turso's built-in replicated database features to prevent loss of critical audit logs/scans.
